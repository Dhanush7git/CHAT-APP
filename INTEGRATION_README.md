# Integrating with a Multilingual Fact Checker

This project provides a React chat client and a Node.js/Socket.IO real-time server. It can be integrated into a multilingual fact-checking application to let users discuss claims and receive fact-checking results in real time.

## Current Architecture

```text
React fact-checker UI
        |
        | Socket.IO connection
        v
Node.js + Socket.IO server
        |
        +--> Fact-checking service
        +--> Translation service
        +--> Database
```

The current prototype connects the client to `http://localhost:5000`. When a client emits a `message` event, the server broadcasts it to every connected client with `io.emit("message", message)`.

For a fact-checker, messages should be sent to a room for a specific claim instead of being broadcast to every user.

## Prerequisites

- Node.js 18 or newer
- The fact-checker frontend and backend repositories
- A translation service, if translations are generated by an external API
- A database, if claims, messages, users, or fact-check results must persist

## Run This Prototype

Install dependencies in both project directories:

```powershell
cd B:\chat-app\server
npm install

cd B:\chat-app\client
npm install
```

Start the backend in one terminal:

```powershell
cd B:\chat-app\server
npm start
```

Start the frontend in another terminal:

```powershell
cd B:\chat-app\client
npm run dev
```

Open `http://localhost:5173/`. The backend listens on port `5000`.

## Recommended Integration Design

### 1. Give every claim an ID

When a user submits a claim, create or reuse a stable identifier such as `claim-123`. Use this ID for fact-check results and chat messages.

```js
const claim = {
  id: "claim-123",
  text: "The original claim text",
  language: "es"
};
```

### 2. Use one Socket.IO room per claim

In the server, join clients to a claim room:

```js
io.on("connection", (socket) => {
  socket.on("join-claim", ({ claimId }) => {
    socket.join(`claim:${claimId}`);
  });

  socket.on("claim-message", (message) => {
    const room = `claim:${message.claimId}`;
    io.to(room).emit("claim-message", message);
  });
});
```

This prevents a message about one claim from appearing in unrelated fact-check discussions.

### 3. Use a structured message format

A structured payload allows the same chat channel to carry user messages, translations, and fact-check results:

```js
{
  id: "message-456",
  claimId: "claim-123",
  type: "user-message",
  text: "¿Es correcta esta afirmación?",
  language: "es",
  translatedText: "Is this claim accurate?",
  senderId: "user-789",
  createdAt: "2026-09-11T17:42:00.000Z"
}
```

Useful `type` values include:

- `user-message` for discussion messages
- `fact-check-request` when a user submits a claim
- `fact-check-result` for the verification outcome
- `translation` for translated content
- `system` for join, leave, or processing notifications

A fact-check result could include additional fields:

```js
{
  id: "message-457",
  claimId: "claim-123",
  type: "fact-check-result",
  verdict: "misleading",
  confidence: 0.91,
  language: "en",
  text: "The claim is misleading.",
  sources: [
    {
      title: "Source title",
      url: "https://example.com/source"
    }
  ]
}
```

## Frontend Integration

The existing chat component creates a Socket.IO client and listens for `message` events. In the fact-checker frontend, connect to the shared backend URL and join the active claim room:

```jsx
import { useEffect } from "react";
import { io } from "socket.io-client";

const socket = io(import.meta.env.VITE_API_URL || "http://localhost:5000");

function ClaimDiscussion({ claimId }) {
  useEffect(() => {
    socket.emit("join-claim", { claimId });

    return () => {
      socket.emit("leave-claim", { claimId });
    };
  }, [claimId]);

  function sendMessage(text, language) {
    socket.emit("claim-message", {
      claimId,
      type: "user-message",
      text,
      language,
      createdAt: new Date().toISOString()
    });
  }

  // Render the discussion and call sendMessage when the user submits text.
}
```

Use an environment variable in the client instead of hard-coding the deployed server URL:

```text
VITE_API_URL=https://api.example.com
```

## Connecting Fact-Checking Results

The fact-checker backend can emit a result after processing a claim:

```js
io.to(`claim:${claimId}`).emit("claim-message", {
  claimId,
  type: "fact-check-result",
  verdict: "true",
  confidence: 0.97,
  language: "en",
  text: "The claim is supported by the available evidence.",
  sources,
  createdAt: new Date().toISOString()
});
```

The frontend can render `fact-check-result` messages differently from normal chat messages, for example with a verdict badge, confidence score, translated explanation, and source links.

## Multilingual Support

Store the original language with every claim and message. A practical flow is:

1. Detect or ask for the language of the submitted claim.
2. Store the original text and language unchanged.
3. Translate the claim into the language used by the fact-checking model, if necessary.
4. Run fact-checking against the normalized claim.
5. Translate the verdict and explanation into each viewer's preferred language.
6. Keep source titles and URLs attached to the result.

Do not overwrite the original text when translating. Store both values:

```js
{
  originalText: "Texto original",
  originalLanguage: "es",
  translatedText: "Original text",
  displayLanguage: "en"
}
```

Translations should be clearly identified as translations. The original claim should remain available so users can compare wording and avoid changing the meaning during translation.

## Backend Migration Checklist

- Move or reuse this project's Socket.IO server inside the fact-checker backend.
- Keep a single Socket.IO server for the frontend and fact-checking API when possible.
- Replace global `io.emit()` calls with claim-specific room broadcasts.
- Add authentication to the Socket.IO handshake.
- Validate `claimId`, message length, language codes, and message types on the server.
- Persist messages and fact-check results if users need history.
- Add rate limiting and moderation for public discussions.
- Configure CORS for the real frontend origin instead of using `origin: "*"`.
- Use HTTPS in production so Socket.IO connections use secure WebSockets.

Server:

```text
PORT=5000
CLIENT_ORIGIN=http://localhost:5173
DATABASE_URL=your-database-connection-string
TRANSLATION_API_KEY=your-translation-service-key
```

Client:

```text
VITE_API_URL=http://localhost:5000
VITE_DEFAULT_LANGUAGE=en
```

Do not commit API keys or database credentials. Add local environment files to `.gitignore`.

## Testing the Integration

1. Start the fact-checker backend and this frontend, or merge the chat server into the fact-checker backend.
2. Open the application in two browser tabs.
3. Open the same claim in both tabs.
4. Confirm both clients join the same claim room.
5. Send a message and confirm only that claim's room receives it.
6. Submit a claim and confirm the fact-check result appears as a structured result message.
7. Test users with different preferred languages.
8. Confirm original text, translated text, verdict, confidence, and sources remain distinguishable.
9. Disconnect one client and confirm the other remains usable.

## Important Prototype Limitations

The current project is a demonstration and does not yet provide:

- User authentication
- Database persistence
- Claim-specific rooms
- Translation functionality
- Fact-checking API integration
- Message validation or moderation
- Production CORS and deployment configuration

These should be added before exposing the chat publicly or using it for official fact-checking discussions.
